# EDA 訂單系統展示腳本

組員 E。以下為約四分鐘展示及錄影分鏡。實際報告時，以已完成並留證的案例為準。

## 開始前

同一台電腦開啟 App、RabbitMQ 管理頁和三個服務的終端機。請先用本機測試副本預演一次，確認 P001 有庫存、付款在 success 模式，並記下通知主 Queue 的 Ready 基準。先停 Notification 和 sample Consumer。準備 A 的架構圖及 E 的測試紀錄。

| 時間 | 畫面與操作 | 口頭說明 |
|---|---|---|
| 0:00–0:35 | 顯示 A 的同步與 EDA 架構對照 | 「以這個訂單案例來說，如果訂單程式依序呼叫庫存、付款和通知，就得知道每個服務的介面，還得等呼叫返回。這次我們讓訂單服務發布 OrderCreated，由 RabbitMQ 分到三個 Queue。」 |
| 0:35–1:10 | 通知停著，從 App 送 P001、數量 1、500.00。複製事件編號 | 「畫面顯示 RabbitMQ 已確認發布。接下來用這個事件編號核對各服務。」 |
| 1:10–1:55 | 顯示庫存、付款的同 ID 結果和通知 Ready；切回 App 查詢 | 「庫存與付款可以先處理。通知目前離線，事件留在通知 Queue，頁面這時還查不到通知紀錄。」 |
| 1:55–2:30 | 啟動 Notification。查同一 ID 的通知與 ACK，比對 Ready | 「通知上線後收到剛剛那筆事件，並保存訂單建立通知。通知可以稍後處理，所以這筆發布及其他兩個服務不用等通知在線。」 |
| 2:30–3:15 | 切付款 `--mode decline`，送另一筆新訂單並查結果。若需展示技術錯誤，切 `--mode error` 送第三筆，再展示 DLQ | 「發布和付款是兩個結果。這筆有 Broker 確認，同時也能看到付款被拒絕。技術例外則由共用層做 NACK，交給死信佇列。」 |
| 3:15–4:00 | Analytics 若已完成端到端驗收，顯示新綁定、基準、下一筆事件及 Git 差異。若仍待驗收，口頭說明規劃及限制 | 「新增統計時，我們把既有事件多綁一個 Queue。訂單端的發布介面仍然相同。整個流程依賴 RabbitMQ、路由設定和事件格式。庫存、付款與通知各自處理，也需要用事件編號去重和追蹤。」 |

## 版面與錄影素材

- 每筆展示先停在 App 的 event_id，再切換到 RabbitMQ 或服務終端機。畫面證據要能認出同一事件。
- 付款模式切換前，先停掉舊的 Payment 程式並核對既有待處理訊息，避免另一個 Consumer 先取走測試事件。
- 若現場使用事先錄好的畫面，標明場次與實測版本。只在老師要求影片時輸出 demo.mp4，並使用實際驗收錄影。
- 截圖與錄影避免露出 .env、帳密、瀏覽器無關分頁。本次輸入使用測試商品。
